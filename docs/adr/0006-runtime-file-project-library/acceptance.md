# 运行时文件项目库：验收与客户端边界

> **权威范围**：ownership epoch 与 runtime revision 的区分、授权、下游客户端和后果 本文中的规范性条款是 ADR-0006 对该主题的唯一权威来源；根 ADR 只保留决定、状态、历史和导航索引。

## Ownership epoch and runtime revision fencing

`storageModeEpoch` fences browser-store ownership and stale tabs; it is not a project or catalog revision. A #45 client coordinates the ownership epoch with the runtime before attaching file adapters, but every target mutation/delete/restore/lifecycle/import command carries its independent expected project revision where applicable, complete `CatalogRevision`, and authenticated `RuntimeCommandContext` through the publication contract. An epoch mismatch requires adapter teardown and ownership recheck; a stale project or catalog revision rejects the requested runtime mutation before library-head publication. Conversely, the #46 settings epoch transition does not change a project revision or authorize a project mutation. The two fences are therefore coordinated at client attachment and recovery, but neither substitutes for the other.

## Authorization and downstream clients

Changing data location does not relax MCP controls. The current bridge keeps its existing browser-backed authorization behavior until #43-#45 land. #45 changes only project/history/asset ownership; settings remain browser-live until #46 and are not exposed to MCP in either stage. In the target runtime, the bridge resolves project data through the command/interface seam above and does not receive raw filesystem access. Opening or reconnecting remains read-only; write, import and run authorization remain separate explicit grants. MCP change sets must carry projectId, expected revision, full `CatalogRevision`, and a command-specific authenticated `RuntimeCommandContext` before calling `applyProjectMutation`, `writeRuntimeAsset`, or an asset lifecycle command. An authorized `.lumina` import first obtains its runtime-allocated operation ID, then calls `applyLibraryTransaction` with that same catalog-pinned context. On reconnect it calls `reconcileLibraryTransaction`, never a blind import retry. Neither calls the legacy revisionless convenience methods. A stale revision/catalog, `authorization_denied`, or post-expiry import ID rejects before a new library-head publication, and disconnect, timeout, token rotation, runtime restart and repair never replay a mutation or billable generation.

An MCP App widget is a downstream proof of concept. It may render a client of this runtime-owned project library only after its own host, authorization and lifecycle questions are tested. Until #48 supplies that contract, every widget write returns typed non-retryable `widget_write_denied`; it is neither a prerequisite for this migration nor an alternative storage owner.

## Required target tests

Target implementation acceptance must parse the exact [admission registry](./admission-registry-v1.json), reject a changed/unknown registry version, and exercise every listed field class, unknown member/node/source-metadata/provider parameter, optional-sensitive omission, MIME, and numeric limit. Fixtures must prove the separate 2 GiB durable asset, 6 GiB import aggregate, 8 GiB streamed archive/migration, 512 MiB buffered browser archive, 4 MiB chunk with a 4,259,840-byte frame, and 64 MiB Gateway-temporary branches; the Gateway fixture must not be accepted as durable-asset evidence. Archive fixtures must prove that the legacy whole-buffer browser verifier rejects before allocation at 512 MiB, that the target runtime accepts ZIP32 at or below its 32-bit container boundary, requires streamed ZIP64 above it, and rejects an 8 GiB-plus-one-byte envelope before staging. They must inject every command context failure and compare-and-swap race for save, rename, viewport, import, direct asset write, candidate mutation, project restore, asset trash restore, and empty-trash, asserting a new full `CatalogRevision` only on success and no staging/head change on each denial/conflict.

The browser/runtime tests must prove that only the browser coordinator opens IndexedDB and that a challenge-bound ledger assertion, not a runtime IndexedDB read, gates target writes. They must cover lost/replayed/expired assertions, pending activation, a bad attachment/epoch/binding, browser clear and authorized repair. Import tests must cover runtime and browser high-water allocation, a post-flush allocation crash gap, lost allocation response, active replay, receipt expiry, and deterministic rejection of every expired burned ID. Trash tests must inject every crash around `manifest.json`, `cleanup.json` authorized/terminal, and `expiry.json` authorized/complete, asserting bounded audit roots and exact-only deletion. These cases supplement, rather than replace, the stale-tab, frozen-store, source-fence, #45 settings-live, #46 settings-freeze, sanitizer, vault, and compatibility-release evidence in the respective authoritative documents.

## Consequences

Today, browser IndexedDB and its browser-only tests remain the current durable behavior at the registered Origin. When #43-#45 implement migration, only `projects`, `history`, and `assets` are read sources before the #45 cutover and then freeze as recovery evidence; the browser settings record remains live. #46 separately migrates non-secret preferences and provider credentials/tokens before freezing `settings`. New work must not claim that either cutover has already happened. Once the target ships, upgrade, Repair, reinstall and ordinary uninstall acceptance must prove the managed library, preferences and credential vault preservation independently of a Chrome profile or registered Origin. The stable Origin remains an entry, bridge and compatibility concern; it does not select the target project library.

This ADR specifies the durable architecture only. It does not implement the filesystem module, browser or HTTP adapters, IndexedDB migration, settings vault, installer changes, or MCP App widget.
