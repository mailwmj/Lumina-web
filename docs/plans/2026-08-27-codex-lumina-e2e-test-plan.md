# Codex 使用 Lumina 的端到端测试方案

记录日期：2026-08-27
适用对象：已安装 Lumina Desktop、希望从 Codex Desktop 操作同一 Lumina 项目的测试人员。

## 1. 目标与通过标准

本方案不把「Codex 能看到 Lumina 工具」当作成功。一次完整通过必须证明以下链路：

```text
Codex plugin -> canvas_open -> Codex 内置浏览器握手 -> 选择项目
  -> 只读画布 -> 显式写入授权 -> 原子画布变更
  -> 单独的生成授权 -> 提交/查询原任务 -> 结果预览与重连恢复
```

通过标准：

1. Codex 从插件调用 `canvas_open` 后，Lumina 在 **Codex 内置浏览器** 打开并完成握手；不得以 connected Chrome 或手动 URL 代替。
2. Codex 能读取指定项目的当前状态，并且项目、历史与资产仍由同一台机器上的 Lumina Runtime 持久保存。
3. 未授权时，Codex 不能写入或发起生成；授权后，允许的画布变更以一个可撤销的变更集提交。
4. 图片生成节点在用户再次单独确认后才会运行；完成、失败、取消和暂时查询故障均有可理解的状态，刷新不会新建一笔生成请求。
5. 断线、token 轮换或 revision 过期后，Codex 不重放旧的写入、导入或生成请求；重新打开并握手后仍能看到同一项目。

本方案不要求测试人员读取 API Key、Runtime 存储路径、资产原文件路径或 MCP token。它们不应出现在截图、日志或 Issue 中。

## 2. 测试前准备

| 项目 | 检查方式 | 预期 |
| --- | --- | --- |
| Lumina Desktop | 使用原生安装器安装；若已有异常先执行 Repair | Runtime 可启动，已有项目保留 |
| Codex plugin | 在 Codex 官方的本地 plugin/marketplace 导入界面导入 `Lumina-Codex-Plugin` | Codex 对话中可发现 Lumina 工具/Skill |
| Node.js | 在启动 Codex 的同一用户环境运行 `node --version` | `>= 18` |
| Codex Desktop | 新建一个正常本地任务，并确认可打开内置浏览器 | 内置浏览器可用 |
| Lumina 项目 | 新建空项目，命名为 `Codex Lumina E2E YYYY-MM-DD` | 没有生产资产，便于判断变更 |
| 生成供应商 | 在 Lumina 设置中配置一个可用图片模型 | 只确认“已配置”；不记录密钥 |

不要把仓库中的 `npm run canvas:codex` 当作普通用户入口。它是显式隔离的开发工具；正式验证通过已安装 Runtime 和已导入 plugin 进行。Codex 的一般产品前置说明以 [OpenAI Docs](https://learn.chatgpt.com/docs) 为准，Lumina 的插件入口、权限与恢复行为以本仓库的 [插件说明](../../plugins/lumina-canvas/README.md) 和 [ADR-0007](../adr/0007-codex-in-app-browser-entry.md) 为准。

## 3. 执行规则与证据

每个用例先记录以下信息，再开始操作：Lumina 版本、Codex 版本、plugin 版本、`node --version`、macOS/Windows 版本、开始时间（UTC）。每例记录“实际结果、状态文本、截图或录屏、是否通过”。

截图应覆盖 Codex 对话、内置浏览器中的 Lumina 状态和相关节点，但必须打码 API Key、token、完整私有提示词、私人资产内容及任何本机路径。一次失败只采集一次完整证据，之后按第 6 节恢复；不要反复点击运行或反复发送相同指令。

## 4. 主路径用例

### TC-01：插件发现与打开

1. 在新 Codex 任务中输入：`打开 Lumina。`
2. 观察 Codex 是否调用 Lumina 的打开能力。
3. 当返回“等待浏览器”时，确认 Codex 在内置浏览器打开返回地址并等待 Lumina 页面连接。

预期：出现 Lumina 页面，且打开目标是 Codex 内置浏览器。若页面要求选择项目，记录为 `awaiting_project`，这不是失败。不得转去 connected Chrome 继续本用例。

### TC-02：选择项目与只读状态

1. 在内置浏览器选择 `Codex Lumina E2E YYYY-MM-DD`。
2. 回到 Codex 输入：`读取当前 Lumina 画布状态，只汇报项目名称、节点数和连接状态，不要修改或运行任何节点。`

预期：Codex 能报告当前项目和画布概况，画布无新增节点。若没有项目，先在页面创建或选择项目，再重新执行本用例；不要把它记录为“插件连接失败”。

### TC-03：未授予写入授权时的拒绝

1. 保持“外部 Agent 写入”关闭。
2. 输入：`在当前画布创建一个图片生成节点，提示词为“测试用红色圆形”，但不要运行。`

预期：Codex 清楚说明当前项目只读或需要用户在 Lumina 页面显式开启有限写入授权；画布中不出现节点。通过条件是“拒绝且无副作用”，不是创建成功。

### TC-04：授权后的原子配置变更

1. 在 Lumina 内置浏览器页面为本会话开启“允许外部 Agent 写入”或等价的有限非计费写入授权。
2. 再输入：`在当前画布创建一个图片生成节点，提示词为“白色背景上的红色圆形，极简矢量风格”，不要运行。完成后告诉我将要运行的节点和模型。`
3. 查看画布、节点属性和撤销栈。

预期：Codex 只提交一次受限变更；出现一个可编辑的生成节点，提示词可见，且不出现结果节点或供应商任务。执行一次 Lumina 撤销应整体撤回该次由 Codex 建立的配置。

### TC-05：运行授权与最小生成

1. 重新完成 TC-04 的配置（若刚才撤销）。
2. 在 Codex 输入：`现在不要运行，只总结该节点的提示词、模型和输出设置，并向我请求运行确认。`
3. 确认 Codex 没有发起生成后，在 Lumina 页面按产品提供的方式显式同意本次运行。
4. 输入：`我已在 Lumina 中确认运行。请运行刚才配置的图片生成节点，并等待终态。`

预期：运行前有独立确认；Codex 只运行已经存在的节点。它使用任务等待/状态查询报告排队、运行、成功、失败或取消中的实际一种，成功后读取压缩预览并确认结果节点与输入节点可追溯关联。未得到第 3 步同意时，发送第 4 步也必须被拒绝或请求确认，不能提交请求。

### TC-06：结果持久化与重开

1. 在成功或失败终态后，记录节点状态；关闭 Lumina 的 Codex 内置浏览器标签。
2. 在同一 Codex 任务输入：`重新打开 Lumina，并读取项目“Codex Lumina E2E YYYY-MM-DD”的当前节点状态；不要修改或运行。`

预期：Codex 建立新的打开/握手过程，而不是复用旧的一次性连接信息；项目、配置节点和已有终态仍存在。若上次成功，预览可重新读取；若失败，失败状态和已有节点仍可见，且不会自动重试。

## 5. 恢复与边界用例

| ID | 操作 | 预期 |
| --- | --- | --- |
| TC-07 | Codex 读取状态后，在 Lumina 页面手动移动或编辑该节点，再要求 Codex 按旧上下文修改它 | Codex 识别 revision 过期；旧写入不落盘、不自动重放。重新 `canvas_open`、读取当前状态后才可提出新的变更。 |
| TC-08 | 在 Codex 正等待或准备执行时刷新/关闭内置浏览器页 | 当前会话失效，旧请求不会在后台提交；重新打开、握手并重新读取后可继续。 |
| TC-09 | 在未确认运行时要求 Codex “直接生图” | Codex 不调用运行操作，而是说明需要当前浏览器中的独立授权。 |
| TC-10 | 用无效或已撤销的供应商配置运行一个已授权节点 | 节点进入明确失败终态，错误可定位到供应商/配置；不创建重复任务，不暴露密钥。 |
| TC-11 | Runtime 已关闭或插件与 Runtime 版本不兼容时输入“打开 Lumina” | 显示可操作的 Runtime 缺失、元数据无效、版本不兼容或 Repair 诊断；不会打开第二个项目库。 |
| TC-12 | 在 Codex 内置浏览器不可用的环境中打开 Lumina | 明确报告内置浏览器是前置条件并停止；不回退到 connected Chrome。 |

可选的编辑权交接验证：当同一项目已被其他手动浏览器会话编辑时，在那个会话中显式批准交接后再让 Codex 写入。预期是旧会话的该项目权限被撤销，Codex 获得当前项目的权限；没有显式交接时不应出现两个长期写入者。

## 6. 失败分流与一次性修复动作

| 看到的现象 | 归类 | 处理后从哪里重试 |
| --- | --- | --- |
| Codex 没有 Lumina 工具或 Skill | plugin 未导入/未启用 | 在 Codex 导入或启用 plugin 后，新建任务，从 TC-01 开始 |
| `requires Node.js >=18` | Codex 启动环境的 Node 不满足 | 安装支持版本、完全重启 Codex，从 TC-01 开始 |
| Runtime 缺失、无法访问、metadata 无效 | Lumina 安装损坏或不完整 | 使用 Lumina Repair，不手改插件文件；从 TC-01 开始 |
| plugin/Runtime 不兼容 | 两者版本线不一致 | Repair Lumina，并在 Codex 中重新导入/更新 plugin；从 TC-01 开始 |
| 页面已开但一直未连接 | 内置浏览器握手失败 | 仅刷新一次该返回地址；仍失败则关闭标签并重新执行 `打开 Lumina` |
| `awaiting_project` | 尚未选择项目 | 在内置浏览器选择项目，从 TC-02 开始 |
| 当前项目只读 | 没有写入授权 | 在 Lumina 页面显式启用本会话外部 Agent 写入，从 TC-03 开始 |
| 要求运行却未发生 | 没有运行授权 | 先在页面单独授权，然后只重试 TC-05 的运行步骤 |
| stale revision、timeout、断线、token 轮换 | 旧会话不可安全重放 | 不要重试原命令；关闭旧操作，重新打开、握手、读取状态，再按当前画布重新提出操作 |
| 生成失败 | 供应商、模型或输入约束 | 保留失败节点和状态，检查 Lumina 设置；修复后由用户明确发起一次新的运行 |

## 7. 建议的最小回归集

每次修复后至少复跑 TC-01、TC-02、TC-03、TC-04、TC-05 和 TC-06。涉及会话、浏览器、权限或 Runtime 的修复，还必须复跑 TC-07 和 TC-08；涉及安装器、Node 检查或 plugin 版本的修复，还必须复跑 TC-11 和 TC-12。

仓库自动合同可作为补充，而不能替代真实 Codex Desktop 证据：

```bash
npm run build
npm run canvas-agent:build
npm run canvas-agent:test
node --test plugins/lumina-canvas/plugin.node-test.mjs
npm run test:local-runtime
```

## 9. 记录结论

完成后将每个用例标记为“通过 / 失败 / 阻塞 / 不适用”。只有 TC-01 至 TC-06 全部通过，才能称为“Codex 中可成功使用 Lumina”；若 TC-05 因供应商额度或配置未完成而阻塞，应把连接和权限链路标注为通过，但不能把端到端生成标注为通过。
