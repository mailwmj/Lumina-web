# 画布图片分辨率加载策略调研

日期：2026-08-19

状态：技术选型建议；第一阶段参数和可见性策略已实施，像素预算待补充原图尺寸元数据后实施

## 1. 结论

全局画布缩放并不能代表图片的实际显示尺寸：节点可以被单独放大。以全局 `1.45x` 或 `1.80x` 作为原图门槛，都会错过“单张图已占据大部分窗口但画布缩放仍低”的场景。

推荐把“视口高清模式”改为以下组合条件：

1. 仅在缩放/平移停止 **180ms** 后判断当前视口；交互开始时立即取消尚未开始的原图任务。
2. 仅对视口中可见面积至少 `25%`、且显示长边达到 `360` 个物理像素的图片节点请求原图。这个显示尺寸同时考虑节点尺寸、画布缩放和屏幕像素密度，按“缩放锚点附近 -> 屏幕中更大 -> 其余”排序，解码并发保持 `4`。
4. 当前高清视口中的原图由请求列表 **pin**，不受“最近 3 张”LRU 淘汰；下一次导航开始时取消未开始任务，最多保留最近 `3` 张已完成原图以平滑过渡；退出检查模式后统一回落预览。
5. 加入一个以自然像素计的 decoded-pixel 预算（首版建议 `48 MP`，约 `183 MiB` 的 RGBA 像素下界），而不是只按张数计。预算不足时优先保留锚点和显示面积更大的节点，其余回落到预览图。

这对应用户的意图：用户通过缩放或手动调整节点大小，看到单张或约三张大图时才加载原图；画布总览中的小图仍只用预览。是否升级只由每张图的实际显示像素决定。

## 2. 当前实现的差异

实施前，原图请求被全局缩放阈值拦截，不能表达“图片已经大到值得看原图”。第一阶段已改为 `25%` 最小可见比例、`360` 物理像素显示门槛和锚点/面积排序；下一阶段再补充自然像素预算。

## 3. 可借鉴的成熟策略

### 3.1 OpenSeadragon：按像素覆盖率选择层级，并限制请求与缓存

OpenSeadragon 的 TileSource 将长边为 `M` 的图片拆为以 2 为幂递增的图像金字塔；其 `maxLevel` 表示可加载的最高层级。[OpenSeadragon TileSource](https://openseadragon.github.io/docs/OpenSeadragon.TileSource.html)

它的 `minPixelRatio` 直接把“当前图层的像素与屏幕像素的匹配程度”作为取舍：默认 `0.5` 会预取更高一级以便缩放时更锐，`1.0` 或更高则减少请求、接受上采样。它也分别提供并发请求上限 `imageLoaderLimit` 和内存图片上限 `maxImageCacheCount`。[OpenSeadragon Options](https://openseadragon.github.io/docs/OpenSeadragon.html)

对 Lumina 的启发不是引入瓦片金字塔。每张生成图目前只有“512px 预览 / 原图”两级，仍应采用相同的三个控制面：

- 显示尺度决定是否值得升级；
- 升级请求有并发上限；
- 已解码原图有明确的驻留预算。

### 3.2 地图 LOD：缩放层级是资源选择边界，不是所有资源常驻的理由

Mapbox Style Specification 把 `maxzoom` 定义为数据可用的最高缩放层级；超过它继续查看时，会使用该最高层级的数据。对于 GeoJSON，较高的 `maxzoom` 明确意味着高缩放时会创建更多细节。[Mapbox Style Spec: Sources](https://docs.mapbox.com/style-spec/reference/sources/)

这说明地图的 LOD 策略把资源选择绑定到屏幕中的实际细节需求，而不是在总览时把全部最高精度常驻。Lumina 以图片的屏幕像素而不是全局缩放数值作为资源边界；低显示尺寸保持 512px 预览，是有意的性能策略，不是降级错误。

### 3.3 浏览器解码：先解码成功，再切换可见源

HTML 标准规定 `HTMLImageElement.decode()` 并行执行解码，Promise 会在解码完成后兑现；标准给出的对比示例指出，直接把未解码图片插入 DOM 可能导致主线程同步解码和掉帧，而先 `decode()` 后再显示可以避免这类掉帧。[WHATWG HTML: `img.decode()`](https://html.spec.whatwg.org/multipage/embedded-content.html#dom-img-decode)

因此原图任务应继续沿用现有“后台 `Image` + `decode()` 成功后才切换 `src`”的机制。不要在 `onMove`/滚轮事件内直接切 `src`，也不应把 `decoding='async'` 当作可绕过队列和内存预算的保证。

## 4. 建议的状态模型

```text
概览模式（当前视口没有满足显示像素门槛的图片）
  -> 所有节点展示 preview，并清理已保留的原图

检查模式（静止 180ms）
  -> 找到可视比例 >= 25% 且显示长边 >= 360 物理像素的图片节点
  -> 按锚点距离、屏幕显示面积排序
  -> 并发 4 个依次 decode；成功后切到 original 并 pin
  -> 已 pin 原图优先占用 48 MP decoded-pixel 预算

缩放/平移重新开始
  -> 取消未开始队列项；最多保留最近 3 张已完成原图，缩放停止后按新视口重新排队

缩出检查模式
  -> 解除 pin 并清空 LRU，所有节点切回 preview
```

`25%` 可见比例避免只露出一条边的节点抢占资源。对于处于视口中央且完整可见的节点，规则仍会使其全部升级，符合“单张或 3 张大图”的检查场景。

## 5. 参数与验收

| 参数 | 建议首值 | 原因 |
| --- | ---: | --- |
| 静止延迟 | `180ms` | 只在用户停止导航后提交后台解码 |
| 解码并发 | `4` | 让同屏约三张大图更快同时变清晰，同时仍避免不受限的批量解码 |
| 高清视口最小可见比例 | `25%` | 避免边缘节点预取；完整可视节点都会加载 |
| 原图显示门槛 | `360` 物理像素 | 预览图接近不足以清晰展示时才排队，避免小节点批量升级 |
| LRU | `3` 张 | 仅平滑下一次导航开始后的短暂过渡，不能取代视口 pin |
| decoded-pixel 预算 | `48 MP` | 约 `48,000,000 * 4 = 183 MiB` 的 RGBA 数据下界；需在真实原图分辨率下实测 |

验收必须覆盖：

1. 在任意画布缩放下，只要一张图片的显示长边达到 `360` 物理像素且可见面积至少 `25%`，静止后就会逐张切为原图；不满足这两个条件的小图维持预览。
2. 高缩放状态下，4 张同屏图片均成功替换原图；从一张切换到另一张不会让前一张立即变糊。
3. 在任务尚未完成时继续滚动，旧视口未开始的任务不再解码，画布拖拽和缩放保持流畅。
4. 超出像素预算时，锚点附近/屏幕面积更大的图片优先清晰；控制台或测试可验证其余节点有意保留预览图，而不是静默失败。
5. 原图解码失败时保留 preview，不出现空白或反复请求循环。

## 6. 不建议的方案

- **把全部已看过的原图永久保留。** 原图解码内存按像素计，不按 JPEG/WebP 文件体积计；长期画布会累积内存和 GPU 压力。
- **只把阈值从 `1.45` 随意调大。** 这能缓解过早加载，但仍无法处理节点尺寸不同、边缘可见和资源优先级。
- **缩放事件中立刻切原图。** 这会把图片解码与持续的画布布局/绘制竞争，最容易产生掉帧和闪烁。
- **现在就引入 Deep Zoom 瓦片。** 当单张原图足以满足检查清晰度时，双层图片和有限缓存已能解决问题；瓦片切图、存储和传输链路属于后续在超大图（例如 8K/高倍局部检查）出现明确指标后才考虑的范围。
